## 计算机和操作系统基础
(善用AI 这一段来自AI)
我先把内存的简单的分成3类：gpu 、cpu 、DMA(本质上还是物理内存条分出来的一块区域)
<br><br>
gpu内存即显存, 其中的分区我暂时不感兴趣

DMA在图形学中主要是能让gpu绕过cpu直接读写主存的一块区域

cpu内存, 这里特指cpu在处理进程的代码时, 能够合法访问的进程空间
<br><br>
首先我们要对内存有深刻的了解, 知道进程空间的概念, 以及如何查看进程空间的范围
一个简单的问题, 有进程A, 有地址0x7fff29102, 如果无法确定地址是否属于进程A, 那还怎么分析下去呢？

一般情况下, 操作系统会提供一些能够陷入内核态接口让我们得到进程的内存列表

例如, Linux系统/proc文件夹下的pid/maps接口

```
cat /proc/2617/maps
cat /proc/$(pidof com.example.foo)/maps
```

列表很长, 其内容的构成, 可以在需要时去谷歌了解
还有更高阶的原理, 内核技术, cpu陷阱等, cpu是如何发现某个地址, 进程是无权访问的？
这些技术可以在需要时去谷歌
<br><br>

## -fstack-protector的原理
arm文档的描述是这样的: 在函数的栈顶插入一个值, 如果栈被越界写了, 这个值一定会变化, 在函数退出时检查这个变量
```
// https://stackoverﬂow.com/questions/10325713/why-does-this-memory-address-fs0x28-fs0x28-have-a-random-value

// 函数开始时使用rax保存一个随机值作为保护变量
0x00007f8e7cf9a8d9 64 48 8b 04 25 28 00 00 00  movq %fs:0x28, %rax
0x00007f953fd5a8e2 48 89 84 24 e0 00 00 00     movq %rax, 0xe0(%rsp)

//在函数结束时把保护变量取到rcx并和rax比较, 如果两个值不相等, 则跳转到错误的标签终止程序
0x00007f8e7cf9acfa 64 48 8b 04 25 28 00 00 00  movq %fs:0x28, %rax
0x00007f8e7cf9ad03 48 8b 8c 24 e0 00 00 00     movq 0xe0(%rsp), %rcx
0x00007f8e7cf9ad0b 48 39 c8                    cmpq %rcx,%rax
0x00007f8e7cf9ad0e 75 0a                       jne  0x7f8e7cf9ad1a ;<+1098>atgpu_program_gles.cpp
......
0x00007f8e7cf9ad1a                             callq 0x7f8e7cﬀ1d10 ;symbolstubfor:__stack_chk_fail

//你问我怎么知道0xe0存储的是保护值？我是从0x00007f953ﬀ9ad03逆推出来的//在实验中肉眼可见, 是否触发堆栈保护, rac和rax的值确实会不一样
```

了解原理之后, 我们可以轻易的知道, -fstack-protector会在函数退出时通知我们堆栈被破坏(修改)了

这意味着这种方式有两个缺点, 无法发现越界读, 无法实时(在当前指令处)立刻暴露内存错误

请再考虑一个问题：假如有一个病毒程序修改了0xf0(%rsp), 非0xe0(%rsp), 甚至修改了堆内存, -fstack-protector还有用么？

## 地址消毒技术
所以需要更强大的功能来保护内存：-fsanitize=address, 地址消毒技术

网络上关于地址消毒的文章大多取自论文AddressSanitizer: A Fast Address Sanity Checker

所以我找了个AI翻译了这篇论文, 花费了大约几个小时, 边读边写下以下内容：
```
影子内存 shadow memory
由于大部分系统都是8字节对齐的, 即malloc返回的堆内存总是8字节对齐, 所以可以使用最少1个字节来表示这8个字节的状态
一般情况下这1个影子字节, 如果是正值, 表示对应的内存可寻址, 如果是负值就是不可寻址(非法访问)
在8字节对齐的内存系统中, 影子地址的计算方式是 shadow_addr = addr >> 3 + offset, offset是一个不太可能被占
用的进程空间地址

红区 redzones
hook内存分配函数malloc free, 在原本申请的基础上多申请一些内存作为红区(堆红区最小32字节)
这样内存的排列就会变成：red mem red mem read
比如原本申请8个字节, 现在变成32+8+32-10+32个字节, 但这些额外字节程序员不感知
当这8个字节被上越界时, 左边的红区会触发, 而下越界时, 则右边的红区会触发, 例如:
char foo[7]; memset(foo, 0, 8);

这种内存错误, 并不一定会被cpu或内核发现(如果无法理解, 请去查阅内存原理和memset等低级函数的源码)
但在红区面前, 简直小儿科, 分分钟抓到
但是！！！以下这种代码, 地址消毒就抓不到了:
int *a = new int[2]
int *u = (int*)((char*)a+6)
*u = 1
XD, 笑死, 本质上这个红区技术, 无法处理刚好落在有效内存区的地址
谷歌的工程师想过解决方案, 但是由于太废性能直接放弃了

(论文还顺便黑了 Valgrind 和 Dr.Menmory, 说他们也做不到)
(“这个技术苹果做不到 鸿蒙项目组的压力也就没这么大了 XD”)
读完文章之后我其实还是对asan能处理越界读(out-of-bounds read)有一些疑惑
实际上还有几个例外场景, 例如结构体, 高性能检测是有代价的
不过我不想再进行下去,  大致了解一下asan的原理就差不多了
使用谷歌搜索"asan out-of-bounds read", 得到一些其他的编译选项, 如-fsanitize=bounds, 可能asan发展了这么久, 早已新增了很多优化
还有一个额外收获是, 了解到了一些做AI或者计算的人可能更需要“超越界检测”这种技术
x = y[MAX_LENGTH + n] 在神经网络场景中, n超大越界
```
